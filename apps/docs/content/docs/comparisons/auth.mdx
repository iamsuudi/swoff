---
title: Authentication
description: Why Swoff's auth module exists — cache eviction on logout prevents data leaks between users.
---

Cached data persists across auth sessions. When user A logs out and user B logs in on a shared device, data from user A is still visible in the cache — a privacy breach. Other caching and data libraries have no concept of auth state, so they cannot prevent this.

Swoff's auth module plumbs auth state through to the cache layer so it can evict everything when the user changes. This is its single purpose. Everything else — offline user display, 401 recovery, auth headers — is secondary convenience.

> See the [Auth guide](/docs/guides/auth) for Swoff's approach, adapter contract, and compatibility. See the [Auth Libraries Reference](/docs/guides/auth-libraries) to identify your auth provider's transmission mechanism. This page focuses on auth-awareness in other tools.

## Comparison table

| Aspect                       | Swoff                                         | TanStack Query / SWR        | Workbox                    | Client DBs (RxDB, PowerSync, ElectricSQL) |
| ---------------------------- | --------------------------------------------- | --------------------------- | -------------------------- | ----------------------------------------- |
| **Auth awareness**           | ✅ Full — auth state plumbed to cache layer   | N/A (app-layer only)        | ❌ No concept of auth      | N/A (different paradigm)                  |
| **Cache eviction on logout** | ✅ Wipes memory, IDB, runtime caches, queue   | N/A (in-memory cache)       | ❌ Cache persists          | N/A (local DB — no auth concept)          |
| **Cross-tab eviction**       | ✅ Broadcasts to all open tabs via SW         | ❌ No cross-tab awareness   | ❌ No cross-tab awareness  | ❌ No cross-tab awareness                 |
| **Offline user display**     | ✅ User data cached in IDB for offline use    | ❌ Not supported            | ❌ Not supported           | ❌ Not supported                          |
| **Token security**           | ✅ Memory-only (bearer) — never on disk       | Developer chooses storage   | N/A                        | N/A                                       |
| **401 detection + recovery** | ✅ SW broadcasts + client refresh via adapter | Developer handles           | ❌ Not supported           | ❌ Not supported                          |
| **Auth header injection**    | ✅ Through adapter `getHeaders()`             | Developer wraps `queryFn`   | ❌ Not supported           | ❌ Not supported                          |
| **Data leak on user switch** | ✅ Not possible — caches evicted on logout    | N/A (in-memory per session) | ❌ Possible — no auth gate | ❌ Possible — no auth gate                |

**TanStack Query / SWR** operate at the app layer (in-memory query cache), not the HTTP cache layer. They have no concept of auth because auth is a network concern, not a query concern. Developers wrap `queryFn` to inject headers and clear the query cache on logout.

**Workbox** is a SW toolkit at the same layer as Swoff but has no auth module. Runtime caches persist indefinitely — data from one user is served to the next until the cache expires or is manually deleted.

**Client DBs** (RxDB, PowerSync, ElectricSQL) embed a local database and sync engine. Sync may support auth headers for initial connection, but there is no concept of token lifecycle, 401 detection, or cache eviction across sessions.
