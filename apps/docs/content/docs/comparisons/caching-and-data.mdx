## Data Layer: HTTP Caching vs Client Databases

The way you cache data on the client determines your entire offline architecture. Swoff operates at the HTTP cache layer — the Service Worker intercepts `fetch` events, caches responses by URL, and serves them on subsequent requests. Data retains its server shape (JSON, HTML, images) and the server remains the single source of truth. Client databases (RxDB, TanStack DB, ElectricSQL, PowerSync) embed a local database engine and synchronize it with the server — they solve a fundamentally different problem, and the choice between them defines your relationship with data, consistency, and complexity.

> See the [Caching Strategy guide](/docs/guides/caching-strategy) and the [Caching System architecture](/docs/architecture/caching) for Swoff's approach. This page focuses on the architectural tradeoffs between SW-level HTTP caching, app-layer server-state libraries, and client-side databases.

## Three layers, three tradeoffs

**SW toolkits** (Workbox, Serwist, vite-plugin-pwa) operate at the same layer as Swoff — the Service Worker `fetch` event, Cache Storage API. The comparison is apples-to-apples: same layer, different design choices.

**Server-state libraries** (TanStack Query, SWR, Apollo Client) operate at the app layer — in-memory query caches, `staleTime`, refetch policies. They manage UI reactivity (loading/error/success states), not HTTP caching. Swoff operates below them at the HTTP layer: responses are cached in the SW regardless of which framework makes the fetch. A real app can use both — TanStack Query for UI state, Swoff for offline HTTP caching — but Swoff already absorbs the caching concern. Server-state libraries become optional reactivity layers on top of Swoff-cached data. Configure their routes as [`"network-only"`](/docs/config/service-worker) in `strategy.patterns` to let your library own data freshness while Swoff keeps handling offline navigation and static assets.

**Client databases** (RxDB, TanStack DB, ElectricSQL, PowerSync) embed a local database engine and synchronize with the server via a sync engine. They solve a different problem — local data queries with offline writes and conflict resolution — but with different costs and constraints than HTTP caching.

## How other tools handle caching

**Workbox:** 5 strategies at the SW level using Cache Storage API. Same layer as Swoff. Fewer strategies (no reactive), no 3-tier config resolution, no per-request header override, no HTML cache isolation.

**Serwist:** Next.js-first evolution of Workbox. Same 5 strategies at the SW level. Adds Next.js App Router awareness (prefetch, RSC caching). Not config-driven — code-only setup.

**TanStack Query / SWR:** App-layer stale-while-revalidate. One strategy — cache-first with staleTime. Cannot intercept native `fetch`, cache HTTP responses for offline navigation, or persist across hard reloads. These operate as a reactivity layer on top of HTTP caching, not a replacement for it.

**Apollo Client:** Normalized GraphQL cache with fetch policies at the app layer. No HTTP response caching — cache is an in-memory entity store keyed by `__typename` + `id`. Cannot serve offline HTML or cache REST endpoints. Body-hash caching and tag-based invalidation are fundamentally different approaches.

## Client databases: a different paradigm

Client databases embed a local DB engine (IndexedDB, SQLite WASM, PGlite) and replicate server data through a sync engine. The app reads and writes to the local DB as if it were primary storage.

**What they do well:**
- Local queries: filter, sort, aggregate data on the client with SQL
- Conflict resolution: CRDTs and custom merge strategies for concurrent edits
- Offline writes: mutations are applied locally and synced when online
- Real-time replication: changes in one tab propagate to others via the sync engine

**Where the paradigm diverges from HTTP caching:**
- **No offline app skeleton.** Client DBs store data locally, but they don't make your app's HTML, CSS, or JavaScript accessible offline. Without a separate Service Worker, the app can't load when offline — you get data without an app to display it.
- **Schema coupling.** Every schema migration — add a column, change a type, rename a field — must be applied to both server and client database schemas.
- **Bulk data replication.** Client-side queries require replicating data to every client. No two clients are guaranteed to be in sync at any moment.
- **WASM cost.** SQLite-in-browser requires a 2–3 MB gzip download (PGlite WASM, SQL.js). On a mobile connection, that's the entire budget for your app's code.
- **Data persistence.** All user data persists in IndexedDB or SQLite indefinitely. On shared devices, one user's data is visible to the next without manual purging.
- **Setup complexity.** Schema definitions, DB initialization, sync engine configuration, and server adapter setup.

**Choose client DBs when** you need local SQL queries, CRDT conflict resolution, or offline-first with a local data engine as primary storage. **Choose Swoff when** you need offline HTTP caching, zero-runtime-deps precaching, tag-based invalidation, and offline navigation — without schema management or WASM downloads.

## Offline Write Queue

Offline write queuing captures mutations (POST, PUT, PATCH, DELETE) when offline and replays them when connectivity returns.

> See the [Offline Mutations guide](/docs/guides/offline-mutations) for Swoff's API and usage. See the [Architecture: Data Sync](/docs/architecture/data-sync) for the internal design (batch queue, dual-replay prevention, auth-aware replay).
