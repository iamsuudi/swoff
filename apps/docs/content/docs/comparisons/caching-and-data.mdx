## Data Layer: HTTP Caching vs Client Databases

The way you cache data on the client determines your entire offline architecture. Swoff operates at the HTTP cache layer — the Service Worker intercepts `fetch` events, caches responses by URL, and serves them on subsequent requests. Data retains its server shape (JSON, HTML, images) and the server remains the single source of truth. Client databases (RxDB, TanStack DB, ElectricSQL, PowerSync) embed a local database engine and synchronize it with the server — they solve a fundamentally different problem, and the choice between them defines your relationship with data, consistency, and complexity.

## How Swoff does it

Swoff implements 6 caching strategies that execute in the SW `fetch` event handler, configured through a 3-tier resolution system:

| Strategy                 | Behavior                                                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `cache-first`            | Return cached immediately, background refresh. Never show stale data longer than the last successful fetch.                |
| `network-first`          | Try network, fall back to cache. Best for live data with offline fallback.                                                 |
| `stale-while-revalidate` | Serve cached (even if stale), then fetch in background. Best for infrequently changing data.                               |
| `cache-only`             | Serve only from cache. Useful for precached assets.                                                                        |
| `network-only`           | Always fetch from network. Never cache. Best for non-cacheable data (auth, nonces).                                        |
| `reactive`               | Serve cache if within `staleTime`, otherwise fetch network + cache. Combines `cache-first` with a freshness threshold.     |

**3-tier resolution:** Per-request via `fetchWithCache({ strategy })` → route pattern in config → global default. Each tier overrides the one below.

**Server is source of truth:** Swoff caches HTTP responses as-is. When data changes, the server sends invalidation signals via SSE/WebSocket, the SW evicts stale entries, and the next request fetches fresh data. No polling, no sync engine, no conflict resolution.

**No schemas, no migrations:** The server defines the API response shape. A new field in the response is automatically cached without any client-side schema change.

## How competitors handle it

**TanStack Query / SWR:** One strategy — stale-while-revalidate (with configurable `staleTime` and `gcTime`). No cache-first, network-first, cache-only, or network-only because these libraries operate at the application layer, not the SW layer. They cannot intercept native `fetch` events or cache HTML/CSS/JS for offline navigation.

**Workbox:** 5 strategies (same as Swoff minus `reactive`), also SW-level, using Cache Storage API. Lacks 3-tier resolution, per-request override via headers, and reactive strategy.

**Apollo Client:** No explicit caching strategies. `InMemoryCache` is a normalized GraphQL cache with fetch policies. App-level only — does not affect native `fetch` caching or offline HTML access.

**Client DBs (RxDB, TanStack DB, ElectricSQL, PowerSync):** Embed a local database engine (IndexedDB, SQLite WASM, PGlite) and replicate server data through a sync engine. The app reads and writes to the local DB as if it were primary storage.

## The client DB approach and its costs

- **No offline app skeleton.** Client DBs store data locally, but they don't make your app's HTML, CSS, or JavaScript accessible offline. Without a separate Service Worker, the app can't load when offline — you get data without an app to display it.
- **Dual-DB maintenance tax.** Every schema migration — add a column, change a type, rename a field — must be applied to both the server database and the client database schema. This is distributed system maintenance in your frontend codebase.
- **Server becomes a data dump.** Client-side queries (filter, sort, search) require replicating bulk data to every client. No single source of truth — no two clients are guaranteed to be in sync at any moment.
- **WASM bloat.** SQLite-in-browser requires a 2–3 MB gzip download (PGlite WASM, SQL.js). On a mobile connection, that's the entire budget for your app's code.
- **Data never auto-clears.** All user data persists in IndexedDB or SQLite indefinitely. On shared devices, one user's data is visible to the next. Privacy-safe logout requires manually purging the entire database.
- **Over-engineered for most use cases.** Forms need draft storage — use native IndexedDB or localStorage, not a sync engine with schema definitions and WASM downloads. Collaborative editing needs WebSocket/WebRTC, not a polling sync engine.

## Offline Write Queue

Offline write queuing captures mutations (POST, PUT, PATCH, DELETE) when offline and replays them when connectivity returns. This is where Swoff's mutation queue differs fundamentally from the client DB approach.

**How Swoff does it:**

Swoff implements a dual-layer mutation queue: primary storage in IndexedDB (survives tab close), with Service Worker fallback via the Background Sync API (survives SW termination).

```
Offline mutation → IndexedDB (queue)
  → processMutationQueue() on online event
    → SW replays mutations sequentially
      → per-mutation online check (aborts batch if offline mid-way)
      → configurable retry with exponential backoff
      → progress events per batch item
      → SUCCESS → invalidate cache tags → refetch → UI updates
      → FAILURE → retry or drop based on maxRetries
```

**Key properties:**

- **Storage:** IndexedDB (persists across tab close, SW restart, browser restart).
- **SW fallback:** When all tabs close, the SW wakes via Background Sync API and replays the queue.
- **Per-mutation online check:** Before each replay, checks `navigator.onLine`. If offline mid-batch, remaining mutations stay queued.
- **Configurable retry:** `maxRetries`, `retryBackoffMs` (exponential), `batchSize`, `batchDelayMs`.
- **Queue introspection:** `getQueuePosition(id)`, `getQueueItems()`, `useMutationQueue()`.
- **Dual-replay prevention:** SW skips Background Sync replay if any client page is open.
- **Auth-aware:** If the auth token expires mid-batch, the SW attempts silent refresh before retrying.

**The Telegram pattern:** Mutations appear as "pending" until the server confirms. No optimistic updates, no phantom ID reconciliation. See [Optimistic Updates](/docs/comparisons/optimistic-updates) for the full design rationale.

**Full system reset — `resetSwoff()`:** Beyond auth-scoped `clearAuth()`, `resetSwoff()` provides a nuclear reset: clears all caches, IndexedDB databases, and localStorage, then unregisters and re-registers the Service Worker. Useful as a "factory reset" for debugging or when the user wants to start completely fresh.
