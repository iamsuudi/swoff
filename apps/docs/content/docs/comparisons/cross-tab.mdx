Cross-tab synchronization keeps cache state consistent across multiple open tabs. When a mutation succeeds in one tab, other tabs should reflect the updated data.

> See the [Tag Invalidation guide](/docs/guides/tag-invalidation#cross-tab-invalidation) for Swoff's approach. This page focuses on cross-tab mechanisms in other tools.

## How competitors handle it

**TanStack Query:** No built-in cross-tab sync. `refetchOnWindowFocus` is a per-tab heuristic. Developers can implement sync manually via `BroadcastChannel`.

**Apollo Client:** No built-in cross-tab sync. Each tab maintains its own in-memory cache.

**RxDB:** Built-in cross-tab replication via `BroadcastChannel`. Changes in one tab are broadcast to all other tabs.

## Why SW broadcast

`BroadcastChannel` is a dedicated browser API for cross-context messaging. Two limitations make the SW approach more robust:

1. **Lost on all tabs closed:** BroadcastChannel is main-thread only. If all tabs close and the SW replays mutations via Background Sync, there is no BroadcastChannel to notify. Swoff updates the cache at the storage layer — when a new tab opens, it reads fresh data directly.

2. **SSE/WebSocket relay cost:** With BroadcastChannel, the tab holding the SSE/WS connection must relay server invalidation messages to other tabs — adding latency and a single point of failure. Swoff's SW holds the connection and broadcasts directly to all tabs.
