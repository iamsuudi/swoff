## Offline-First Architecture

Build web apps where the **app shell works offline** and **data is handled intelligently** — reads cached, mutations queued when offline.

## Principles

1. **Offline App Shell** — All routes and static assets cached via Service Worker
2. **Smart Data Handling** — Read requests cached, mutations queued when offline
3. **Backend Optional** — Works with your existing server, or go full offline (Tier 2)

## Two Tiers

### Tier 1: App Shell + Smart Data (General Pattern)

Works with your existing backend:

```
┌─────────────────────────────────────────────────┐
│                 Browser (Client)                  │
│                                                   │
│  ┌──────────────┐  ┌──────────────────────────┐ │
│  │ Service      │  │  App Logic               │ │
│  │ Worker       │  │  (React/Vue)             │ │
│  │              │  │                          │ │
│  │ - App shell  │  │  - Read from Cache API   │ │
│  │   cache      │  │  - Queue mutations       │ │
│  │ - Read cache │  │  - Sync when online       │ │
│  └──────────────┘  └──────────────────────────┘ │
└─────────────────────────────────────────────────┘
         │                              ▲
         │ Fetch read                    │
         │ Cache write                   │ Sync queued
         ▼                              │
┌─────────────────────┐                │
│  Your Backend API   │────────────────┘
│  (dynamic data)     │  Return data
└─────────────────────┘
```

### Tier 2: Full Offline (Special Case)

No backend needed (like Budget Manager):

```
┌────────────────────────┐
│     Browser Tab         │
│  ┌──────────────────┐ │
│  │  React/Vue App   │ │
│  │  IndexedDB data  │ │
│  └──────────────────┘ │
│  ┌──────────────────┐ │
│  │ Service Worker    │ │
│  │ (cache storage)   │ │
│  └──────────────────┘ │
└────────────────────────┘
```

## Storage Strategy by Tier

### Tier 1 (General Pattern)

| API                | Purpose                          |
| ------------------ | -------------------------------- |
| **Cache API**      | Cache read request responses     |
| **IndexedDB**      | Queue mutations when offline     |
| **localStorage**   | Settings, metadata, SW version   |
| **sessionStorage** | Session state (cleared on close) |

### Tier 2 (Full Offline - Budget Manager Pattern)

| API                | Purpose                        |
| ------------------ | ------------------------------ |
| **IndexedDB**      | Full database for all app data |
| **localStorage**   | Settings, metadata             |
| **sessionStorage** | Session state                  |
| **Cache API**      | App shell assets only          |

## Data Flow (Tier 1 - General Pattern)

**Online (First Visit):**

1. Browser loads `index.html`
2. SW registers and caches app shell (all routes, static assets)
3. App fetches data from backend, caches read responses in Cache API
4. Mutations sent to backend normally

**Offline:**

1. SW serves app shell from cache (instant)
2. Read requests served from Cache API
3. Mutations queued in IndexedDB
4. When back online: queued mutations synced to backend

## Session Management

Survive refreshes, clear on tab close:

```typescript
// On login
sessionStorage.setItem("auth", "true");

// On page load
if (sessionStorage.getItem("auth") === "true") {
  showApp();
} else {
  showLogin();
}
```

## Offline Checklist (Tier 1 - General)

- [ ] SW caches all static assets and routes
- [ ] Read requests cached for offline access
- [ ] Mutation queue implemented (IndexedDB)
- [ ] Sync logic for queued mutations
- [ ] App shell works without network

## Offline Checklist (Tier 2 - Full Offline)

- [ ] SW caches all static assets and routes
- [ ] IndexedDB initialized as full database
- [ ] All CRUD operations use IndexedDB
- [ ] App works 100% offline (no backend needed)
