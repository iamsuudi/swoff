# Swoff Demo App — React + Vite

An offline-first PWA example built with [Swoff](https://github.com/iamsuudi/swoff), React 19, Vite 8, and Tailwind CSS v4. Demonstrates service worker caching, tag-based cache invalidation, offline mutation queuing, background sync, three backend auth patterns, a GraphQL wrapper with cache-key hashing, and Web Push notifications.

## Quick Start

```bash
# 1. Start the API server (choose one auth pattern)
npm run server:bearer

# 2. In another terminal, start the dev server
npm run dev
```

Open http://localhost:5173 and log in with `demo@swoff.dev` / `password123`.

## Auth Patterns

This example ships with three API servers demonstrating different authentication strategies. All three share the same `server/db.json` for data persistence and expose identical routes (`/api/login`, `/api/register`, `/api/logout`, `/api/refresh`, `/api/me`, and Notes CRUD). Only the auth layer differs. Each server also mounts a shared GraphQL endpoint at `/graphql` and shared push notification endpoints under `/api/push/*`.

### 1. Bearer Token (`server:bearer`)

| Aspect         | How it works                                                              |
| -------------- | ------------------------------------------------------------------------- |
| Auth mechanism | JWT returned in login response body                                       |
| Client storage | Token stored in memory via `setAuth({ token, user })`                     |
| Request header | `Authorization: Bearer <token>` via `fetchWithCache(url, { auth: true })` |
| Swoff config   | `"auth": { "type": "bearer" }`                                            |

The client sends the token on every request. The server validates it from the `Authorization` header. This is the default pattern used by the current app.

**Login response:**

```json
{
  "token": "eyJ...",
  "user": { "id": 1, "email": "...", "name": "..." },
  "expiresAt": 1718000000000
}
```

**Authenticate middleware:** Reads `req.headers.authorization`, strips `Bearer ` prefix, verifies JWT.

**Run:** `npm run server:bearer`

### 2. Cookie JWT (`server:cookies`)

| Aspect         | How it works                                           |
| -------------- | ------------------------------------------------------ |
| Auth mechanism | JWT stored in an HttpOnly cookie set by the server     |
| Client storage | No token handling — browser sends cookie automatically |
| Request header | Cookie sent automatically. No `Authorization` needed   |
| Swoff config   | `"auth": { "type": "cookie" }`                         |

The server signs the JWT and sets it as a `Set-Cookie` header. The browser attaches the cookie to every request automatically. The client never touches the token.

**Login response:**

```json
{ "user": { "id": 1, "email": "...", "name": "..." } }
```

(A `Set-Cookie` header is also sent, invisible to JavaScript.)

**Authenticate middleware:** Reads `req.cookies.swoff_token`, verifies JWT.

**Run:** `npm run server:cookies`

### 3. Session (`server:session`)

| Aspect         | How it works                                           |
| -------------- | ------------------------------------------------------ |
| Auth mechanism | Opaque session ID in an HttpOnly cookie                |
| Server storage | In-memory `Map` synced to `db.json`                    |
| Client storage | No token handling — browser sends cookie automatically |
| Swoff config   | Same as cookie: `"auth": { "type": "cookie" }`         |

No JWT involved. The server creates a session (UUID), stores it in memory, and sets the session ID as an `HttpOnly` cookie. On each request it looks up the session to find the user.

**Login response:**

```json
{ "user": { "id": 1, "email": "...", "name": "..." } }
```

**Authenticate middleware:** Reads `req.cookies.swoff_session`, looks up the session in the store, retrieves the user.

**Run:** `npm run server:session`

### Switching Between Auth Types

1. Stop the current server.
2. Change `swoff.config.json` `auth.type` to `"bearer"`, `"cookie"`, or `"custom"`.
3. Run `npx @swoff/cli generate` to regenerate the `swoff/` code.
4. Start the corresponding server with the appropriate npm script.

**Note:** Session-based auth uses the same client-side behavior as cookie-based JWT (both rely on `HttpOnly` cookies). Use `"auth.type": "cookie"` in the Swoff config for both cookie JWT and session servers — the only difference is on the backend.

## Swoff Features Demonstrated

| Feature                | What it does                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Service Worker**     | Caches API responses with configurable strategies (network-first for `/api/*`, cache-first for static assets). Auto-activates on update.                                                                   |
| **Cache Invalidation** | Tag-based cache busting. After a mutation, stale cache entries are purged by resource tags (e.g., `notes`, `note:42`).                                                                                     |
| **Mutation Queue**     | Offline writes are stored in IndexedDB and replayed when the connection restores. Configurable batch size, rate limiting, and exponential backoff.                                                         |
| **Background Sync**    | The service worker processes queued mutations even after the tab is closed.                                                                                                                                |
| **Auth**               | Bearer token management (or cookie/session) with automatic 401 handling, token refresh, and user caching for offline access.                                                                               |
| **Cross-Tab Sync**     | Auth state and cache invalidations broadcast across open tabs.                                                                                                                                             |
| **PWA**                | App install prompt (via `InstallButton`) and manifest generation.                                                                                                                                          |
| **GraphQL Wrapper**    | `queryGql()` / `mutateGql()` functions backed by the same caching, auth, and offline queue as REST. Query bodies are hashed for deterministic cache keys; operation names auto-generate invalidation tags. |
| **Push Notifications** | Bell toggle in the header to subscribe/unsubscribe. Every CRUD operation (REST + GraphQL) automatically fires a push notification to all subscribers. Expired endpoints are cleaned up on send. |

## How Offline Works

1. **Online:** All requests go through `fetchWithCache()` with `{ auth: true }`. Responses are cached with tags.
2. **Offline write:** When `navigator.onLine === false`, `queueMutation()` stores the mutation in IndexedDB. A yellow banner appears on the notes list.
3. **Connection restored:** The mutation queue auto-processes. On success, cached entries are invalidated and the UI refreshes via `mutation-sync-complete` and `cache-invalidated` custom events.
4. **Offline read:** Cached API responses are served from the service worker cache. The app works without a network.

## GraphQL

All three API servers mount a shared GraphQL endpoint at `/graphql`. The Swoff-generated `swoff/gql-wrapper.ts` provides three functions that hook into the same caching, auth, and offline queue as the REST layer:

- `queryGql<T>(query, variables?, options?)` — cached read, uses SHA-256 body hash as the SW cache key
- `mutateGql<T>(mutation, variables?, options?)` — write with auto-tag invalidation, optionally queued offline
- `fetchWithGql<T>(query, options?)` — underlying function with full control

**Try it with curl:**

```bash
# Query notes
curl -s http://localhost:3001/graphql \
  -H "Authorization: Bearer $(curl -s -X POST http://localhost:3001/api/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"demo@swoff.dev","password":"password123"}' | node -e "process.stdin.on('data',d=>console.log(JSON.parse(d).token))")" \
  -H "Content-Type: application/json" \
  -d '{"query":"query { notes { id title description priority } }"}'
```

**From the React app:**

```typescript
import { queryGql, mutateGql } from "../swoff/gql-wrapper.ts";

// Query (cached, respects SW cache)
const { data, fromCache } = await queryGql(
  "query Notes { notes { id title } }",
);

// Mutation (auto-invalidates note tags)
const { data: created } = await mutateGql(
  "mutation CreateNote($title: String!, $desc: String!) { createNote(title: $title, description: $desc) { id title } }",
  { title: "From GraphQL", desc: "Created via gql-wrapper" },
  { auth: true },
);
```

The schema mirrors the REST endpoints and includes `me`, `notes`, `note(id)` queries and `createNote`, `updateNote`, `deleteNote` mutations — all authenticated via the same middleware that protects the REST routes.

## Push Notifications

Push notifications are fully integrated end-to-end: a **subscribe toggle in the header**, **auto-trigger on every mutation** (both REST and GraphQL), and **automatic cleanup of expired subscriptions**.

### Architecture

| Layer | File | Role |
|---|---|---|
| Client library | `swoff/push.ts` | Browser-side subscribe/unsubscribe via Push API, IndexedDB persistence |
| React hook | `swoff/hooks/usePushSubscription.tsx` | `usePushSubscription(vapidKey)` returning `{ subscribed, subscription, loading, subscribe, unsubscribe }` |
| Subscribe button | `src/components/PushSubscribeButton.tsx` | Bell toggle in the header — calls `subscribeToPush()` + `POST /api/push/subscribe` on enable, `POST /api/push/unsubscribe` + `unsubscribeFromPush()` on disable |
| Server endpoints | `server/push.js` (`setupPush`) | `POST /api/push/subscribe`, `/api/push/unsubscribe`, `/api/push/trigger` — subscriptions stored in `db.json` |
| Auto-trigger function | `server/push.js` (`triggerPushNotification`) | Reads all subscriptions, sends via `web-push`, removes expired (410/404), writes back |
| REST trigger | `bearer.js`, `cookies.js`, `session.js` | Every POST/PUT/DELETE on `/api/notes` calls `triggerPushNotification()` asynchronously |
| GraphQL trigger | `server/graphql.js` | Every `createNote`/`updateNote`/`deleteNote` resolver fires an `onMutation` callback → `triggerPushNotification()` |

### Subscribe in the browser

Once logged in, click the **🔔 On** / **🔕 Off** toggle in the header to enable or disable push notifications for this device. The button uses `usePushSubscription(vapidPublicKey)` which:

1. Requests `Notification.permission` (browser prompt)
2. Calls `registration.pushManager.subscribe()` with the VAPID public key
3. Persists the subscription to IndexedDB
4. Sends the subscription object to `POST /api/push/subscribe` on the server

### Auto-trigger on mutations

Every note mutation automatically sends a push to all subscribed devices:

| Action | Notification title | Notification body |
|---|---|---|
| Create note | `Note created` | `"<title>" added` |
| Update note | `Note updated` | `"<title>" updated` |
| Delete note | `Note deleted` | `"<title>" removed` |

This works for **both REST and GraphQL** — the [`triggerPushNotification`](./server/push.js) function is called from each REST handler and each GraphQL resolver after `writeDb(db)`. The call is fire-and-forget (`.catch(() => {})`) so it never blocks the API response.

### Demo: cross-tab push

1. Open **two browser tabs** and log in as `demo@swoff.dev` in both
2. Click the bell toggle to **🔔 On** in both tabs (accept the permission prompt)
3. Create, edit, or delete a note in **tab A**
4. A push notification pops up in **tab B** with the note title
5. The notification also appears even if tab B is in the background

```bash
curl -X POST http://localhost:3001/api/push/trigger \
```

## Login Flow (Client)

The `LoginPage` and `RegisterPage` handle both auth patterns flexibly:

```typescript
const data = await res.json();
await setAuth({
  ...(data.token && { token: data.token }), // bearer only
  ...(data.expiresAt && { expiresAt: data.expiresAt }), // bearer only
  user: data.user,
});
```

- **Bearer servers** return `{ token, user, expiresAt }` — all three are stored.
- **Cookie/session servers** return only `{ user }` — just the user is stored; the cookie is set by the server automatically.

After login, `flushMutations()` replays any queued offline operations, and a `sw-auth-state-change` event triggers the UI to update.

## The `User` Type

Defined in `src/types.ts` and used throughout the app:

```typescript
export interface User {
  id: number;
  email: string;
  name: string;
}
```

The generated `swoff/auth/store.ts` and `swoff/auth/user.ts` import and use this type instead of `Record<string, unknown>`. This is a customization on top of the generated code — if you re-run `swoff generate`, you'll need to re-apply this change.
